Connect provider tools through SELA

Operator guide for connecting upstream MCP servers using OAuth and reviewing their tools before agent access.

Private development preview. These are operator setup instructions for the current SELA MCP client. Vercel approval, a reviewer-accessible build or environment, and live authenticated connection tests are pending.

1. Obtain a SELA environment

SELA is currently provided as a private operator-managed environment. Obtain the approved build, deployment instructions and a security-administrator account from KRONEUS. This draft does not offer a public download or a provisioned reviewer tenant.

For a local test, run the supplied SELA backend and console on the same workstation used for provider sign-in. Open http://127.0.0.1:8000/dashboard/mcp_connectors.html and sign in through SELA's normal authentication flow.

Remote environments must use HTTPS. A local loopback callback works only on the workstation running SELA; it is not a public reviewer endpoint.

2. Configure OAuth on the SELA backend

  1. Set SELA_MCP_OAUTH_CALLBACK_URL to the exact callback registered with the provider. For this local test: http://127.0.0.1:8000/api/mcp-connect/oauth/callback.
  2. Configure an encryption key for stored tokens: SELA_MCP_OAUTH_KEY, a base64-encoded key of at least 32 bytes, or the existing application ENCRYPTION_KEY. Keep this key in the backend secret store.
  3. Store the provider's client secret in the backend secret store. The console accepts a reference such as sela-secret://vercel_oauth_client_secret; it does not accept a literal client secret. Configure that reference to resolve before starting OAuth.
  4. Use SELA's approved outbound network route for discovery, token exchange and upstream MCP traffic.

SELA discovers the provider's protected-resource and authorization-server metadata, uses authorization code flow with PKCE S256, and binds a single-use expiring state to the connection. Access and refresh tokens are stored encrypted in the backend. The browser and enrolled agents receive connection status, not those tokens.

3. Register the provider client

ProviderClient registration and test endpoint
GitHubRegister SELA's own GitHub App or OAuth App. GitHub does not support dynamic client registration. For least-privilege tests, use a GitHub App with read-only repository contents and selected test repositories. Upstream endpoint: https://api.githubcopilot.com/mcp/readonly.
VercelRequest review and callback approval for SELA as an MCP client. An ordinary Vercel sign-in application does not establish MCP client approval. Upstream endpoint: https://mcp.vercel.com. Use the client registration and authentication method approved by Vercel.

Current Vercel metadata advertises confidential-client authentication methods. This SELA build supports a supplied client ID and backend client secret using client_secret_basic or client_secret_post. Its generic public-client dynamic registration requires advertised support for none; that path cannot be assumed to work with Vercel.

4. Connect from the console

  1. Open MCP Connectors as a SELA security administrator.
  2. Choose the GitHub or Vercel app card. Register a connector with its official endpoint and OAuth authentication, or open the existing matching connector.
  3. Open OAuth connection settings. Enter SELA's registered client ID and the backend sela-secret:// reference. Request only the necessary provider scopes; do not copy the full advertised scope list.
  4. Choose Sign in. Complete the provider's sign-in and review the requested access in the popup.
  5. The provider returns to SELA's registered callback. Return to the console and check the OAuth connection status. An error or expired state requires starting a fresh sign-in.
  6. Discover the server's tools and review their inventory, custody configuration and per-tool policy before allowing agent use.

Saving browser preferences does not apply a backend connection. Provider consent does not grant an agent a SELA tool permission. Employee identity verification, agent enrollment and execution admission are separate controls.

5. Reviewer test procedure

Prerequisites: an approved SELA build or accessible test environment, a SELA security-administrator account, the provider-approved SELA client configuration, a configured backend secret reference, and an isolated provider test account/project. These reviewer prerequisites must be supplied before a reproducible external review.

  1. Complete steps 2–4 and confirm that the status is connected without exposing tokens to the browser.
  2. Initialize the upstream MCP connection and discover its tools. Record the returned inventory separately from any execution permission.
  3. Permit one harmless read against a designated test resource. For Vercel, select a read-only project metadata tool from the discovered inventory; do not assume every Vercel tool is read-only.
  4. Call that tool through SELA using an enrolled test agent and the required SELA admission. Verify the response and the corresponding decision/execution record.
  5. Attempt a tool or resource outside the test agent's permission. Verify denial before the provider operation and confirm no external effect.
  6. Revoke the connection in SELA and verify that subsequent authenticated upstream use is refused.

A successful OAuth connection or tool listing proves connectivity only. Protected execution, frozen prompt/action binding, pod containment and independent forensic proof require their own same-execution evidence and negative tests.
